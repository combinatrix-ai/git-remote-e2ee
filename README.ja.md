## なぜエンドツーエンド暗号化なのか

**Git ホスティングの「プライベート」は、他人から見えないという意味で、ホスティング事業者から見えないという意味ではありません。**
GitHub や GitLab のプライベートリポジトリは、事業者が読める形で保存されています。ファイルの中身、コミットメッセージ、ブランチ名、誰が何を書いたかまで、すべてです。だからこそ Web で差分を見たり CI を動かしたりできるのですが、裏を返せば、事業者側に届く人なら誰でも読めるということでもあります。情報漏えい、流出したアクセストークンや連携アプリ、内部の人間、法的な開示要求、自分では選べない規約の変更などがその経路です。

**エンドツーエンド暗号化（E2EE）は、鍵を自分の端末に置きます。** リポジトリはアップロードする前に手元で暗号化され、許可した端末だけが復号できます。保存先にあるのは読めないデータだけです。事業者が侵害されても、提出を求められても、渡せる中身がありません。保存されたデータが改ざんされれば、クライアントが気づいて受け取りを拒否します。

`git-remote-e2ee` は、これを Git の下で行います。`e2ee::` で始まる URL をリモートに追加すれば、あとはいつもどおりに作業できます。

**向いている用途:** 個人のメモや日記、公開前の研究、第三者のストレージに置く必要がある受託・NDA案件のコード、非公開の設定ファイル、自分で管理していない場所へのバックアップ。

**引き換えになるもの:** 保存先が中身を読めない以上、保存先で中身を見せることもできません。Web での差分表示、プルリクエストのレビュー、コード検索、ホスト側の CI は平文に対しては使えません。また、鍵は自分で管理します。許可した鍵をすべて失うと、誰にも復元できません。

## git-remote-e2ee の特長

Git リポジトリ全体の暗号化自体は新しいものではなく、[`git-remote-gcrypt`](https://github.com/spwhitton/git-remote-gcrypt) が長年実現してきました。`git-remote-e2ee` はその目的を引き継ぎ、暗号化リモートを日常的に使ううえで困る点を3つ解決します。

- **速い: push では変わった分だけをアップロードします。** アップロードするのは新しい Git の pack と少しのメタデータだけで（端末1台でごく小さなコミットなら合計 3〜4 KiB）、どのバックエンドでも同じです。gcrypt は Git や SFTP のバックエンドでは push のたびに履歴全体を上げ直し、予告なく repack することもあります。ただし現時点では、Git ホストを保存先にすると操作のたびに暗号化された carrier リポジトリ全体を clone するため、そこではダウンロードはまだ差分になっていません。
- **安全: 黙って force push されません。** fast-forward の確認はクライアントで行い、保存先の `HEAD` は compare-and-swap でしか動きません。2人が同時に push すると片方が勝ち、もう片方は普通に拒否されます。gcrypt では push が実質すべて force push なので、後の push が先の push を消してしまうことがあります。
- **マスターキーなし: 端末ごとに別の鍵を持ちます。** 配って回る長期のリポジトリパスワードや共有の秘密鍵はありません。公開のたびに新しいランダムな鍵を作り、許可された端末それぞれに個別に届けます。管理者は公開鍵で端末を追加でき、履歴を書き換えずに1台ずつ取り消せます。transcrypt は1つのパスワードを共有し、git-crypt は1つのリポジトリ鍵を共有していて、アクセスの取り消しに対応していません。

内部では、Git はいつもどおり手元で動きます。ヘルパーが Git から受け取った pack と ref を暗号化し、中身の見えない変更不可のオブジェクトとしてアップロードしてから、中身の見えない `HEAD` ポインタを1つだけアトミックに更新します。現在使える保存先は、**ローカルまたはマウントしたディレクトリ**と、暗号文の運び役として使う**通常の Git リモート**（GitHub、GitLab、bare リポジトリ）です。他のツールのほうが向いている場合も含めた詳しい比較は[他のツールとの比較](#他のツールとの比較)にあります。

## クイックスタート

ソースからインストールします（Rust のツールチェーンが必要です）。セットアップ用の CLI `git-e2ee` と、Git が `e2ee::` URL で呼び出すヘルパー `git-remote-e2ee` の2つが入ります。どちらも `PATH` に置いてください。

```console
cargo install --git https://github.com/combinatrix-ai/git-remote-e2ee
```

空の GitHub リポジトリを暗号化された保存先にして、既存のプロジェクトを push します。

```console
git-e2ee keygen --output ~/.config/git-e2ee/notes.key.json
git-e2ee carrier-init \
  --remote https://github.com/you/notes-encrypted.git \
  --key ~/.config/git-e2ee/notes.key.json

cd my-notes
git remote add private 'e2ee::git+https://github.com/you/notes-encrypted.git'
git config remote.private.e2ee-key ~/.config/git-e2ee/notes.key.json
git push -u private main
```

以降は `git pull` と `git push` をいつもどおり使えます。鍵ファイルは手元に残ります。コミットせず、安全な場所に控えを取ってください。

2台目の端末では、その端末用の鍵を作り、公開鍵のほうを許可します。手順は[利用ガイド](docs/guide.md#add-a-second-device)（英語）にあります。ディレクトリを保存先にする方法、clone、端末の取り消しもそちらで説明しています。

## 他のツールとの比較

Git を暗号化するツールには大きく2つの系統があり、解決している問題が違います。

- **ファイルフィルタ型**（[`git-crypt`](https://github.com/AGWA/git-crypt)、[`transcrypt`](https://github.com/elasticdog/transcrypt)）は、普通のリポジトリの中で、選んだファイルの中身だけを暗号化します。リポジトリの構造と履歴はホストから見えますが、暗号化していない部分については普段どおりホストの機能が使えます。
- **暗号化リモート型**（[`git-remote-gcrypt`](https://github.com/spwhitton/git-remote-gcrypt)、`git-remote-e2ee`）は、履歴を含めてリポジトリ全体を暗号化します。ホストに見えるのは中身の読めないデータだけで、内側のリポジトリについては何もわかりません。

### 保存先に何がわかるか

| | 通常のプライベートリポジトリ | `git-crypt` | `transcrypt` | `git-remote-gcrypt` | `git-remote-e2ee` |
|---|:---:|:---:|:---:|:---:|:---:|
| 保護対象に選んだファイルの中身 | 見える | 隠れる | 隠れる | 隠れる | 隠れる |
| それ以外のファイルの中身 | 見える | 見える | 見える | 隠れる | 隠れる |
| ファイル名とディレクトリ構成 | 見える | 見える | 見える | 隠れる | 隠れる |
| コミットメッセージ・作者・日時 | 見える | 見える | 見える | 隠れる | 隠れる |
| ブランチ名とコミットグラフ | 見える | 見える | 見える | 隠れる | 隠れる |
| 変更されたファイル・サイズ・同一ファイル | 見える | 見える¹ | 見える | 隠れる | 隠れる |
| push した時刻とおおよその量 | 見える | 見える | 見える | 見える | 見える |
| 共同作業者の鍵 | アカウント一覧 | 鍵のフィンガープリント² | —（共有パスワード） | 人数のみ³ | 人数・公開鍵・権限⁴ |

○ 対応 · △ 条件付き · × 非対応

1. git-crypt の README に、ファイルが変わったかどうか、長さ、2つのファイルが同一かどうかは隠さないと明記されています。
2. git-crypt の GPG モードでは、リポジトリ鍵を利用者ごとに暗号化し、鍵のフィンガープリントの名前で `.git-crypt/` 以下にコミットします。
3. gcrypt は既定で受信者の鍵 ID を隠します（`gpg -R`）。暗号化された鍵パケットの数はわかります。
4. 各端末は復号の前に自分宛ての封筒を見つける必要があるため、ポリシーは平文の構造を持ちます。そのため保存先には、端末の数、リポジトリごとの公開鍵、権限、ポリシーの変更が見えます。端末鍵をリポジトリ間で使い回さないでください。
5. gcrypt はローカルと rsync のバックエンドでは差分転送ですが、[ドキュメント](https://manpages.debian.org/trixie/git-remote-gcrypt/git-remote-gcrypt.1.en.html)によると Git や SFTP のバックエンドでは push のたびに履歴全体をアップロードします。また、予告なくリモートを repack することがあります。
6. git-crypt は暗号化したファイルの中身を認証しますが、ファイル名、履歴、どのファイルが暗号化されているかは通常の Git データです。
7. transcrypt は認証のない CBC を使っており、README で暗号文の malleability を既知の制約として挙げています。
8. git-crypt の README に、アクセスの取り消しには対応していないと明記されています。鍵を替えるには、保護したファイルを手作業で暗号化し直す必要があります。
9. `gcrypt.participants` から参加者を外すことはできますが、取り消しの手順は文書化されていません。
10. 取り消すと、履歴を書き換えずに新しい鍵が発行されます。ここに挙げたどのツールでも、その端末がすでに持っているデータは取り戻せません。
11. プロトコル上は3つの権限を分けていますが、現在の CLI で付与できるのは「読み書き」か「読み書きと管理」のどちらかです。
12. gcrypt の push は実質的にすべて force push です。明示的な force を求めるオプションは事故を防ぎますが、同時に書き込む人同士の調整はしません。
13. 暗号化したファイルは、変更すると前の版と無関係な暗号文になるため、Git が差分圧縮できません。
14. 一度同期したことのある clone は、巻き戻しや分岐した履歴を拒否します。まったく新しい clone は、外部のアンカーがないと見分けられません。[セキュリティモデル](#セキュリティモデル)を参照してください。
15. 現在 push できるのは `refs/heads/*` だけです。タグの push とブランチの削除は、何も公開せずに失敗します。
16. アップロードはどのバックエンドでも差分です。Git ホストを保存先にした場合、現在の実装は操作ごとに carrier リポジトリ全体を clone するので、永続キャッシュが入るまでは fetch や push のたびに暗号化された履歴全体もダウンロードします。

### その他の方法

- **Keybase の暗号化 Git** はエンドツーエンド暗号化されていますが、Keybase のサービスでしか使えません。
- **bare リポジトリを暗号化ファイルシステムの上に置く**方法（rclone crypt、Cryptomator、gocryptfs）は、中身は隠せますが、リポジトリのファイル構成、サイズ、更新のパターンは隠せません。同期サービス経由で2台から同時に push すると、リポジトリが壊れることもあります。
- **git-annex の暗号化 special remote** が守るのは annex された大きなファイルで、Git の履歴そのものではありません。

### 他のツールのほうが向いている場合

- **git-crypt**: 秘密にしたいのが一部のファイルだけで、残りは GitHub や GitLab で普段どおり扱いたい。
- **transcrypt**: 同上で、共有パスワードとシェルだけの簡単な構成で構わない。
- **git-remote-gcrypt**: 実績のあるリポジトリ全体の暗号化ツールがほしく、すでに GPG を使っていて、ローカルか rsync のバックエンドを使える。
- **通常のプライベートリポジトリ**: ホスティング先を信頼でき、プルリクエスト、検索、プレビュー、CI を使いたい。
- **成熟したもの全般**: 安定した形式、復旧ツール、タグ、shallow clone が今すぐ必要。

`git-remote-e2ee` を選ぶのは、リポジトリ全体と履歴を保存先から隠す必要があり、共同作業者がそれぞれ自分の鍵を持つべきで、信頼できない保存先でも Git の普段どおりの競合の扱いがほしいときです。

## セキュリティモデル

保存先は悪意があるものとして扱います。`git-remote-e2ee` が目指す保証は次のとおりです。

- 内側の中身と Git メタデータ（ファイル、パス、ref、オブジェクト ID、作者、メッセージ）の機密性
- 取得したすべての状態の真正性と完全性
- 一度同期した clone に対する連続性。巻き戻しや分岐は拒否されます。
- 取り消された端末には、取り消し以降に公開されたものの鍵が渡らないこと

次のことは**防げません**。

- 保存先がデータを消したり、サービスを止めたりすること
- まったく新しい clone に古い履歴や分岐した履歴を見せること、クライアントごとに違う履歴を見せること（外部のアンカーが必要で、ロードマップにあります）
- 権限のある書き込み者による破壊的な変更
- 取り消された端末が、取り消し前に読めたものを読むこと
- トラフィック分析（更新時刻、オブジェクトのサイズ、全体の増え方は見えます）
- 将来の量子計算機による攻撃（鍵交換は X25519 です）

鍵は過去向きの鎖になっています。現在の鍵でそれ以前の履歴をすべて復号できるので、新しい端末もリポジトリ全体を読めますが、古い鍵でそれより新しいものは復号できません。これは key regression であって、すでに公開された履歴に対する前方秘匿性ではありません。脅威モデルの詳細は [docs/design.md](docs/design.md) と [docs/spec.md](docs/spec.md)、問題の報告は [SECURITY.md](SECURITY.md) を参照してください。

## 性能

全体の転送は通常の Git とほぼ同じ時間で済み、小さな更新は速いままです。867 MiB の Godot の履歴を使い、ローカルファイルシステムのバックエンドで1回ずつ測った結果です。

| 操作 | 通常の Git | `git-remote-gcrypt` | `git-remote-e2ee` |
|---|---:|---:|---:|
| 最初の push | 30.51 秒 | 12.26 秒 | 13.78 秒 |
| 新規の fetch | 30.26 秒 | 30.78 秒 | 31.75 秒 |
| ごく小さな push | 0.17 秒 | 0.54 秒 | 0.08 秒 |
| ごく小さな更新の fetch | 0.12 秒 | 0.50 秒 | 0.09 秒 |

通常の Git とは単純に比べられません。Git サーバーはオブジェクトを索引し、fetch のたびに pack を作りますが、暗号化リモートは中身の見えない pack を保存してそのまま再生します。単純な保存先では効率的ですが、partial clone のようなサーバー側の機能は使えなくなります。更新ごとに保存されるのは新しい pack とメタデータだけで、小さなコミットなら端末1台で合計 3〜4 KiB、読み手100人では1回の更新あたり約 30 KiB になります。読み手を1人追加しても、既存の pack は1バイトも書き換わりませんでした。これらはディレクトリのバックエンドでの数値で、Git carrier のバックエンドは現在、操作ごとに carrier を clone し直します。測定方法、その他のケース、制約は [docs/benchmarks.md](docs/benchmarks.md) にあります。

## よくある質問

**GitHub のリポジトリはどう見えますか？**
`git-remote-e2ee` というブランチが1つあり、`e2ee/` 以下に暗号文が入っています。無関係なブランチと同居できます。手で編集しないでください。

**鍵をなくしたらどうなりますか？**
アクセスできる端末が1台も残っていなければ、データは失われます。設計上、復旧サービスはありません。少なくとも1つの管理者鍵と、その `.admin-state.json` をオフラインで控えておいてください。

**端末を取り消すと、古い履歴も見えなくなりますか？**
いいえ。その端末がすでに復号できたものはそのまま残ります。取り消し以降に公開されたものは読めません。

**プルリクエストのレビューはできますか？**
ホスト上ではできません。鍵を持つマシンでブランチを fetch して手元で差分を見るか、CI ランナーに専用の端末鍵を渡してください。

**保存先がリポジトリを巻き戻せますか？**
古いデータを返すことはできます。一度同期した clone はそれを検知して拒否しますが、新しい clone はまだ見分けられません。

**耐量子暗号ですか？**
いいえ。今日の暗号文を記録しておき、将来 X25519 を破れるようになった攻撃者は、それを読める可能性があります。

## 現状とロードマップ

現在動くもの: clone、fetch、pull、push、ディレクトリと carrier-Git のバックエンド、端末ごとの鍵、端末の追加と取り消し、差分転送、巻き戻しと競合の検知。

予定: 管理者の M-of-N 承認、鍵の復旧と交換、push の競合に負けたときの自動再試行、S3 の条件付き書き込みバックエンド、ガベージコレクションと compaction、タグとブランチの削除、shallow clone と partial clone、透明性ログによる任意のアンカー。
